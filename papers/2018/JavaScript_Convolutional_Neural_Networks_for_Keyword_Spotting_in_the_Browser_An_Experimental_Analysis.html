一句话：getUserMedia → 前端提 log-mel → 纯 JS 手写 res8 前向——零插件零服务器全本地；首次把网络瘦身（BN 缩放因子 L1 + 通道剪枝）引入 KWS：延迟 30ms→10ms（−66%），准确率 94%→90%。

1问题：Web 语音交互的云端枷锁

TL;DR
  • 云端处理 = 网络往返 + 服务器推理的延迟——交互式应用要即时响应，这条链路天生慢。
  • 语音上云有隐私风险；而 JS 是解释型语言、矩阵运算慢、当时无 WebGPU——浏览器跑 CNN 有真实的技术天花板。
  • 模型还要靠网络传输加载——既要小又要快。

2机制：BN γ 是免费的通道重要性标尺

稀疏训练

对 BN 缩放因子 γ 加 L1 正则——不重要的通道 γ 被压向 0，重要性被「显式标记」出来。

通道剪枝

γ 低于阈值的通道连同卷积核整体移除——结构化剪枝，直接减少卷积计算量。

微调恢复

剪后微调补回精度——三步闭环让「删通道」变成可控操作。

res8 的适配性

Sainath 2015 的 8 层残差小骨架（~100K 参数）——专为 KWS 设计、网络传输可接受、JS 实现不易出错。
图 2 · 左：γ 分布在 L1 正则前后的对比——弱通道被压向 0 成为可剪枝标记；右：res8 的浏览器适配理由与瘦身后的连锁收益。
L_total = L_CE + λ · Σ_γ |γ| → 剪掉 γ < 阈值的通道 → 微调 30ms → 10ms（−66%）, 94% → 90%
人话：BN 层每个通道都有一个「音量旋钮」γ。训练时额外惩罚所有旋钮的绝对值，不重要的通道旋钮会被拧到接近零——对输出几乎没贡献的通道，删掉它白赚算力。删完再微调一遍把精度补回来。

4边界：JS 天花板

无 GPU 加速

WebGPU 当时未标准化——纯 JS 解释执行，复杂模型在浏览器可能跑不动实时。

架构上限

res8 的 94% 不算高——CRNN/注意力更强但 JS 运行效率未验证。

缺 WASM/量化对比

未试 WebAssembly（近原生速度）· 未试 INT8——两条最显然的加速路线缺席。

词汇量有限

GSC v1 仅 30 词——真实复杂场景的表现未经验证。

5判断：能带走的三句话

JUDGEMENT

弱算力平台上压缩的杠杆更大：同样的剪枝在 GPU 上只是省一点电，在 JS 解释执行上是延迟的三分之二——压缩技术的价值与执行环境的「贫富程度」成正比，选压缩手段前先看目标平台的算力税率。

BN γ 是免费的稀疏化抓手：不改变训练流程、不加辅助损失网络、剪枝标准现成——「用已有参数当重要性代理」是结构化压缩最省工程量的套路。

平台可行性研究有自己的价值序列：先证明 possible（本文），再证明 easy（TF.js），最后证明 fast（WebGPU）——三个阶段回答不同问题，不要用第三阶段的标准否定第一阶段的贡献。
