## 问题陈述

### 问题背景和领域痛点

智能音箱、可穿戴设备这类边缘计算设备离我们的生活环境越来越近，它们持续产生的语音数据正是关键词识别（Keyword Spotting, KWS）等机器学习应用的核心燃料。但恰恰因为数据采集发生在卧室内、手腕上，隐私问题变得尖锐：AI 公司通过激进收集边缘设备用户数据来改进服务质量的做法，与欧盟近年批准的《通用数据保护条例》（GDPR）对用户数据收集的强限制正面冲突。如何在合规前提下利用这些分散在设备端的宝贵数据，是论文开篇立起的整个问题空间。

论文梳理的方案光谱分三层。第一层是可证明隐私的密码学方案——安全多方计算（MPC）和同态加密（HE），它们能给出严格隐私保证，但计算与通信开销巨大，对公开的跨设备（cross-device）场景不实用，更适合少数机构间的跨孤岛（cross-silo）协作。第二层是启发式隐私方案——Google 提出的联邦学习（FL）：数据不出设备，每个用户在本地持有一份完整模型副本、用私有数据训练，周期性把参数更新发给服务器；服务器按 FedAvg 对所有用户更新做加权平均得到全局模型，再下发进入下一轮。FL 已在 Google Assistant 和 Google 键盘上规模化落地。第三层是本文所在的 TinyML 语境：Giménez 等人（论文引用[3]，Electronics 2022）首次把 FL 带进微控制器社区，在一块 TinyML 开发板上用 FL 训练了一个 16K 参数的 2 层 MLP，完成二分类的关键词判别任务。

痛点就在这第三层暴露。FL 有一个硬性前提：用户必须有能力在本地训练**整个模型**。对内存和功耗极度受限的嵌入式系统，这个前提对工业规模的模型根本不成立。论文的实验平台 Arduino Nano 33 BLE Sense 只有 256KB SRAM 和 1MB Flash（详见第 3.1 节硬件描述），而训练一个模型所需的运行时内存远大于推理——除了参数本身，还要容纳前向激活缓存、反向梯度、以及带动量的 SGD 额外维护一份同尺寸动量缓冲。粗略地说，float32 训练态内存开销至少是参数量的三到四倍，这还没算音频缓冲和 MFCC 特征缓存。[3] 之所以只能用 16K 参数的小 MLP，正是被微控制器的 SRAM 逼的——但 16K 参数的二分类器离"有意义的工业任务"还很远。

### 现有方法的具体不足

- **FL 的内存墙**：FL 要求整个模型驻留设备并完成本地前向、反向全流程。模型一大，SRAM 装不下训练态的三件套（参数、梯度、动量），任务直接不可行。这不是精度问题，是可行性问题——FL 在微控制器上只能训得动玩具模型（[3] 的 16K 参数 2 层 MLP、二分类），无法处理更复杂的数据集和用例。
- **MPC/HE 的开销墙**：可证明隐私的密码学方案计算和通信开销过大，不适合公用的跨设备场景，只能退到跨孤岛场景使用。
- **Split Learning（SL）的串行瓶颈**：分割学习（Vepakomma 等人 2018 年提出，论文引用[7]）把模型切成客户端和服务器两半，客户端只跑前几层，激活值和标签送到服务器续算。但原始 SL 的多客户端协作是轮流的（round-robin），一个客户端训完才轮到下一个，并行性差。
- **SFL 自身的两个已知缺陷**：分割联邦学习（Thapa 等人 AAAI 2022 提出，论文引用[5]）把 FL 的模型聚合思想并入 SL 解决了并行问题，但论文第 2.2 节明确承认 SFL 有两个公认弱点——通信开销偏高（每步都要在设备与服务器间往返激活值和梯度），以及易受模型反演攻击（model inversion attack，客户端每步都要把标签连同激活值一起发给服务器，攻击面比 FL 大）。近期工作（引用[1]的异步训练降通信、引用[6]的模型反演防御）只部分缓解，作者强调部署前仍需谨慎评估。
- **常规 SFL 的推理依赖**：分割式训练出的模型，推理时同样依赖与服务器的远程通信——设备只持有前几层，后半截在云上。这对低延迟、离线可用的关键词识别场景（唤醒词必须本地即时响应）是结构性缺陷。

### 该论文要解决的关键挑战

论文要回答的核心问题是：**能否在一块 256KB SRAM 的微控制器上，让设备端只持有一个极小的客户端切片，参与训练一个远超其内存容量的完整大模型，并在训练结束后把压缩过的整模型塞回设备实现独立推理？** 拆开是四个子挑战：（1）在 SRAM 只够容纳第一层网络、训练 batch size 只能取 1 的约束下，把 SFL 的前向切割、梯度回传、模型同步全流程在真实微控制器上跑通并验证正确性；（2）在同等硬件约束下证明 SFL 能用上 FL 用不上的大模型从而拿到更高精度（最终在英文数字数据集上比 SOTA 的 FL 实现高 13.89 个百分点）；（3）打通"训练态在服务器、推理态回设备"的框架转换流水线（PyTorch 到 Keras 再到 int8 量化的 TFLite），消掉 SFL 推理依赖服务器的缺陷；（4）在只有一块板子的条件下模拟多客户端联邦训练。

## 方法论

### 整体架构设计和设计动机

**硬件平台**（第 3.1 节）：Arduino Nano 33 BLE 板（Sense 版带麦克风），原文描述为"2-bit ARM Cortex-M4 CPU running at 64 MHz with 256KB SRAM and 1MB Flash memory, operating at 3.3V"——其中"2-bit"显系笔误（Cortex-M4 是 32 位核，该板实际搭载 nRF52840），但 64MHz 主频、256KB SRAM、1MB Flash、3.3V 供电这组约束是全文所有设计决策的出发点。

**系统角色划分**（Figure 1）：一块 Arduino 板充当真实客户端；一台 PC 同时扮演三个角色——服务器（跑 PyTorch 实现的服务器侧模型）、总控（管理串口通信时序）、以及虚拟的其余客户端（用 PyTorch 复刻客户端模型加 MFCC 前端来模拟多板）。板与 PC 之间用串口链路连接。数据流上有一个关键的工程妥协：由于板子尚不支持数据标注和存储功能，作者把客户端私有数据先存在 PC 上、经串口推给板子，板子在本地完成 MFCC 特征提取后再喂给客户端侧模型——原始音频确实在板上完成了特征化，但"数据原生于设备"这一环是模拟的。板载麦克风可以采实时音频做推理，但受限于存储空间且难以让用户在板上同步打标签，真采集训练数据留作未来工作。

**为什么切在第一层、为什么客户端这么小**：分割点选得极浅，客户端只保留整个网络的第一层。客户端侧模型只有两个候选形态（第 3.3 节）：一个 1 层 MLP（650×25，与[3]一致）或一个 1 层 Conv2D（12×1×3×3）。动机很直接——第一层的输入是全网络最大的张量（650 维 MFCC 展平特征），但只要把输出宽度压到 25 或 12 个通道，板上参数量就被钉死在千级；后续所有大层全部住在没有内存限制、训练速度快的服务器上。作者明说：用 SFL 就是为了"能用非常大的模型训练，因为服务器没有内存限制"（第 1 节）。

**模型动物园**（Table 1）：

| 模型 | 客户端（板上） | 服务器（PC） |
|---|---|---|
| Model 1（MLP） | FC25 | FC7 |
| Model 2（CNN） | Conv12×3×3 | Conv16×3×3 → FC128 → FC7 |
| Model 3（CNN） | Conv12×3×3 | Conv30×3×3 → FC256 → FC7 |

作者对这套容量阶梯的解释（第 3.3 节）：MLP 对特征线性可分的简单数据集已经够用，服务器侧加复杂度收益很小；小数据集上"大 CNN 反而容易过拟合、验证精度更差"；而更大的 ENdigits 数据集上 CNN 显著优于 MLP，所以服务器侧做了两个档位的 Conv 后端（16 通道接 FC128，30 通道接 FC256）。MLP 基线是 2 层 FC（650×25×7），论文称总参数 650×25+25×7=4725、其中板上 4550——注意这行算术按原式直接计算应为 16425（650×25=16250，加 25×7=175），4725 与 4550 两个数对不上式子，原文如此，疑似排版或输入笔误，引用时需留意。

### 核心算法的数学原理

Algorithm 1 给出了 SFL 的完整形式化。设 $M$ 个客户端各自持有私有数据 $(X_i, Y_i)$，$L$ 层的完整 DNN 被切成服务器侧模型 $S$（参数 $W_S$）与各客户端侧模型 $C_i$（参数 $W_{C_i}$）：

1. **模型同步**：每个 epoch 开始时做联邦平均 $C^* = \frac{1}{M}\sum_{i=1}^{M} C_i$，然后所有客户端对齐 $C_i \leftarrow C^*$。这一步就是 FL 的 FedAvg 聚合思想作用于客户端切片——它使得各客户端在异构数据上训出的不同本地切片副本被周期性拉回共识，也是 SFL 区别于轮流训练的 SL 的关键。
2. **并行客户端前向**：对每个 batch，客户端 $i$ 并行计算 $A_i = C_i(W_{C_i}; x_i)$，把激活值 $A_i$ 连同标签 $y_i$ 经串口发给服务器。
3. **串行服务器前向反传**：服务器依次（Sequential）对每个客户端算交叉熵损失 $l = l_{CE}(S(W_S; A_i),\ y_i)$，对损失反向传播得到对激活值的梯度 $\nabla_{A_i} l$，回传给客户端，并更新 $W_S$。
4. **并行客户端反传**：客户端收到 $\nabla_{A_i} l$ 后在本地继续链式反传，更新 $W_{C_i}$。

数学上这就是把链式法则在切割点处断开：$\frac{\partial l}{\partial W_{C_i}} = \frac{\partial l}{\partial A_i} \cdot \frac{\partial A_i}{\partial W_{C_i}}$，第二个因子所需的局部雅可比只在客户端算，第一个因子由服务器算好传回。设备端因此永远不需要知道 $W_S$ 的形状，服务器也永远不接触原始音频 $x_i$——隐私边界落在切割面上。代价是每一步训练都要两次穿越串口（激活值上行、梯度下行），这正是第 2.2 节承认的通信开销弱点的来源；同时标签随激活值明文上行，构成模型反演攻击面的来源。

**MFCC 前端**（第 3.2 节）：音频输入 1 秒、16000 个采样点（即 16kHz 采样率）。MFCC 超参：13 个系数，帧长 0.02 秒、步进 0.02 秒（无重叠），32 个滤波器组，FFT 长度 256，归一化窗口 101。MFCC 用 Edge Impulse 的嵌入式实现——可直接部署到板上；同时用 Python 复刻了一份 MFCC 用于 PC 侧全在线模拟训练，目的是加速超参搜索（板上跑 MFCC 太慢，扫超参不现实）。1 秒音频按 20ms 无重叠分帧约得 49-50 帧，13 系数展平即约 650 维输入，与客户端 MLP 的 650 输入维度对上。

**训练超参**（第 3.4 节）：batch size 固定为 1（板上资源所限）；学习率 CNN 用 0.005、MLP 用 0.0005（相差十倍，理由未展开——从结果看 CNN 靠卷积归纳偏置能吃更大步长，MLP 只能小步慢走）；SGD 动量 0.6；训练验证划分 9:1；SFL 训练轮数固定 3 个 epoch。

### 关键技术创新一：在微控制器上首次落地 SFL（极浅切割 + 双框架异构实现）

这是论文的第一贡献：SFL 首次被部署到一块超低功耗、低成本的微控制器上，做一个有意义的多类数字关键词识别任务（此前[3]的 FL 工作只是二分类）。工程上最有含金量的是**异构双端实现**（第 3.5 节）：客户端模型用 C++ 手写在板上（连着嵌入式 MFCC 一起），服务器模型用 PyTorch 写在 PC 上；另用 PyTorch 复刻客户端模型加 MFCC 前端来虚拟出其余客户端，拼成多客户端 SFL。这意味着切割点两侧跑在不同框架、不同精度环境里，梯度经串口在 C++ 世界和 PyTorch 世界之间往返——能收敛本身就验证了两侧前向/反向语义的一致性。多客户端训练虽然实现了，但作者坦承是串行处理（future work 里列了并行化）。

### 关键技术创新二："训练大模型、部署压缩模型"的解耦流水线

这是全文最聪明的工程洞察（贡献第三条，第 5.3 节）：**训练态内存需求和推理态内存需求是两码事，SFL 把前者甩给服务器，后者用压缩+量化收回设备。** 常规 SFL 的推理也要依赖服务器通信，论文的做法是训练收敛后，服务器把客户端切片与服务器切片拼成完整全局模型，从 PyTorch 手工搬权重到 Keras（两框架参数布局不同，作者自述"惹了 tons of trouble"），再转成开启 int8 量化的 TFLite 模型，直接部署回 Arduino 板做本地低延迟推理。推理只需参数本身（int8 后每参数 1 字节，是 float32 的四分之一）加一层激活缓存，不需要梯度、动量和训练 batch 的中间量——这就是为什么一个训练时板上根本装不下的模型，部署时反而塞得回去。训练与部署的内存约束由此解耦。

### 关键技术创新三：用模型容量阶梯实证"SFL 打破内存墙"

实验设计的核心对照（第 5.2 节）：MLP 模型（Model 1）代表 FL 在该硬件上能达到的性能——因为 FL 根本没法在板上训练整个 CNN；两个 CNN 模型（Model 2/3）只有在 SFL 下才成为可能。三个模型在同一数据集、同一训练协议下比验证精度，把"内存墙→只能用小模型→精度天花板"这条因果链变成了可测量的数字（详见实验部分）。这个对照设计本身就是论文的论证骨架：SFL 的价值不在于训练算法更优，而在于**解除了模型容量的人为封顶**。

### 与现有方法的技术差异

- **对 FL（McMahan 等，FedAvg）**：FL 传参数更新、整模型驻设备；SFL 传中间激活与切割点梯度、设备只驻第一层。通信物从"参数差"变成"每步的激活/梯度张量"，频度更高但单次更小（取决于切割点深度）。FL 在 256KB SRAM 上训不动大模型，SFL 可以。
- **对 SL（Vepakomma 等）**：SL 客户端轮流训练、无聚合；SFL 每 epoch 做 FedAvg 式的客户端切片聚合，支持（形式上的）并行多客户端。
- **对[3]的板上 FL**：[3]用 16K 参数 2 层 MLP 做二分类；本文同等硬件上做多类（7 类）识别，且服务器侧可以放到数百万参数级别的 CNN。
- **对原版 SFL（Thapa 等，SplitFed）**：原版跑在工作站/服务器级硬件；本文是 MCU 级落地，并追加了"训练后压缩回设备推理"的部署闭环——原版 SFL 不解决推理依赖服务器的问题。
- **对集中式训练**：集中式要上传原始数据，隐私上不可接受；SFL 原始数据纯本地处理，论文结论宣称 SFL 兼得"比 FL 更高的效用"与"比集中式更好的隐私"。注意这只是启发式隐私，无形式化保证，与 MPC/HE 的可证明隐私有本质差距。

## 实验结果

### 使用的数据集及其规模

两个数据集（第 3.2 节）：

- **CNdigits（中文数字，自采）**：作者用开源 Edge Impulse 平台在线采集自己念的中文数字，类别为数字 1 到 5，外加"silence"（静音）与"unknown"（未知）共 **7 类**，每类 **50 条**，合计 350 条。规模极小、说话人单一，属于概念验证性质。
- **ENdigits（英文数字）**：取自 Warden 2018 年的 Speech Commands 数据集（引用[8]）中与上述对应的类别，共 **7000 条**。作为更大、更真实的集合承担主要性能对比。

两个集合用同一套 MFCC 前端和 9:1 训练验证划分。论文未报告类别分布是否均衡、验证集具体规模、说话人数量等细节。

### 评估指标的定义和选择理由

唯一指标是**验证精度**（第 4 节：训好的模型在验证集上的预测正确率）。选择理由可以从任务性质理解：7 类平衡分类、且论文要比较的是学习方案（FL 可达容量 vs SFL 可达容量）而不是部署指标，准确率是最直接的效用度量。但深读必须指出指标面的单薄：**论文未报告**量化后模型体积、板上推理延迟、单轮训练耗时、串口通信总量、能耗、混淆矩阵、各类别的查准查全——而这些恰是 TinyML 论文通常必须交代的部署侧证据。摘要里"low latency"（低延迟）没有任何数字支撑；5.5 节自述因框架转换延误"没来得及做最终部署与板上测试"，等于推理闭环只走到"转成 TFLite"这一步。

### 与基线方法和SOTA的详细对比

**正确性验证**（第 5.1 节，Figure 2）：Model 1（MLP）用 SFL 在 CNdigits 上训练，曲线显示模型在约 **70 轮内快速收敛**，达到 **90% 以上**的精度（训练与验证曲线均给出）。这一组实验的意义是排除"实现有 bug"——异构双端、串口传梯度的流水线能收敛到与任务难度匹配的精度，SFL 实现被验证正确。小数据集上 MLP 足矣，作者也确认"不需要很大的 CNN 模型"。

**SFL 对 FL 的核心对比**（第 5.2 节，Figure 3 训练精度 / Figure 4 验证精度）：ENdigits 上三个模型同台。所有模型在 2 个 epoch 后训练精度都能超过 80%；由于 batch size 为 1 的 SGD，训练期精度波动很大；CNN 收敛速度明显快于 MLP。最终验证精度：**Model 1（MLP，即 FL 在此硬件的上限形态）66.25%，Model 2（小 CNN）78.29%，Model 3（大 CNN）80.14%**（Figure 4）。80.14% − 66.25% = **13.89 个百分点**，即摘要宣称的"比 SOTA FL 实现（[3]）高 13.89%"的出处。结论链条：更大更复杂的模型在 ENdigits 上性能更高，而只有 SFL 用得上大模型，因此 SFL 优于 FL。

需要指出的对比缺陷：这是"最强 SFL 模型"对"FL 被内存墙锁死后的唯一可用模型"的比较，容量与结构两个变量混在一起（架构混杂因子），并非同容量下 SFL 训练算法本身更优的证明——SFL 的胜利本质是内存可行性带来的容量红利。此外论文未与集中式训练的精度上界对照（服务器本来就有全部可模拟的数据，补一条中心化基线成本很低），未做多随机种子重复，66.25/78.29/80.14 均为单次运行数字。

**部署侧**（第 5.3 节）：服务器收集收敛后的全局模型（客户端切片+服务器切片），经 PyTorch→Keras→TFLite（int8 量化）转换，声称可直接部署到 Arduino 板本地推理。量化后精度损失、模型字节数均**论文未报告**。按 Table 1 拓扑自行粗算可感受量级：1 秒音频的 MFCC 约 13×49 的单通道图，Model 3 服务器侧 Conv30×3×3（12 通道入）输出约 30×11×47≈1.55 万维，接 FC256 仅该层权重约 400 万，int8 量化后约 4MB，已超 nRF52840 的 1MB Flash——这也从侧面解释了为何 Model 3 的实际板上部署未能完成；而 Model 1（约 1.6 万参数，即使按论文口径 4725）量化后远小于 Flash，才是真正落得回设备的形态。此段为笔者按拓扑推算，供工程判断参考，非论文报告数字。

### 消融实验的发现

论文没有正式的消融表，实际承担消融职能的是**模型容量阶梯**（Table 1 × Figure 2-4）与数据集规模的交叉：

- **容量×数据规模的交互**：小数据集（CNdigits，350 条）上 MLP 已达 90%+，作者观察到"大 CNN 在小数据上过拟合、验证精度反而更差"（第 3.3 节，属定性陈述，未给出曲线）；大数据集（ENdigits，7000 条）上容量红利兑现，66.25%→80.14% 单调上升。这条"小数据小模型、大数据大模型"的经验与泛化理论常识一致，也是全文最有迁移价值的工程判断之一。
- **优化噪声**：batch size 1 导致精度曲线大幅波动（第 5.2 节），这是 MCU 内存约束直接渗入优化动力学的实证——若 SRAM 更宽裕能放大 batch，曲线应显著平滑。
- **收敛速度**：CNN 比 MLP 收敛更快（Figure 3），可归因于卷积核在时频图上的局部平移不变性先验对语音特征的适配。

**缺失的消融**（均论文未报告）：切割点深度的影响（为什么切第一层而不是第二层——若切深一层，通信的激活张量变小但板上内存变大，存在权衡曲线，论文没碰）；客户端模型形态 MLP 与 Conv12×1×3×3 的对照（文中并列给出两个候选但没拆开比较）；客户端数量 $M$ 的具体取值与缩放规律；聚合频率（每 epoch 一次是否最优）；串口波特率与每样本通信字节数；同步 SGD 与异步的对照。这些空白勾出了后续工作的空间。

## 主要贡献

论文自列三条贡献（第 1 节），加上实现层可归纳为四点：

1. **首次把 SFL 部署到微控制器**：在一块超低功耗、低成本（64MHz/256KB SRAM/1MB Flash 级）的嵌入式系统上跑通分割联邦学习全流程，任务是有意义的多类数字关键词识别，而非此前 TinyML-FL 工作[3]的二分类玩具任务。
2. **实证 SFL 打破训练内存墙**：证明 SFL 允许设备参与远超其内存容量的模型训练，大模型（CNN）因此取得比 FL 硬件约束下唯一可用的小 MLP 高 13.89 个百分点（80.14% 对 66.25%，Figure 4）的验证精度——FL 的短板被归因为容量封顶而非算法本身。
3. **补上"推理回设备"的闭环**：训练后将整模型压缩、量化为 int8 TFLite 发回设备本地推理，消解常规 SFL 推理依赖服务器通信的结构缺陷；"训练态内存甩给服务器、推理态内存压回设备"的解耦是本文最可转述的工程思路。
4. **多客户端训练的原型实现**：通过 PyTorch 虚拟客户端实现多客户端 SFL 训练（串行模式），并打通 C++（板上客户端）与 PyTorch（服务器及虚拟客户端）异构双端的梯度互操作。

## 局限性与展望

### 方法的技术局限性

- **SFL 的固有弱点原样继承**：通信开销（每步激活上行+梯度下行穿串口）与模型反演攻击脆弱性（标签随激活明文上传）是论文第 2.2 节自认的两个已知问题，本文未做任何实测或加固，只提醒"需谨慎评估"。串口通信量、带宽需求全文未报告。
- **隐私只是启发式的**：与 MPC/HE 的可证明隐私不同，SFL/FL 的隐私边界依赖"原始数据不出设备"这一假设，对梯度泄露类攻击无形式化保证；论文对此未展开任何攻击实验。
- **训练协议被硬件削足适履**：batch size 锁死为 1、epoch 固定 3、动量 0.6 的一组超参未经充分搜索（板上 MFCC 太慢导致超参搜索被迫在 PC 模拟环境做），优化质量天花板可疑。
- **部署流水线带伤**：作者发现的 PyTorch→ONNX→TensorFlow→TFLite 标准链路因 TFLite Micro 不支持 Transpose 算子（用于对齐 PyTorch 与 TensorFlow 的卷积权重布局差异）而走不通，被迫手工搬权重过 Keras，过程代价大且易错——这也是最终没来得及做板上部署测试的直接原因（第 5.5 节）。
- **多客户端是串行模拟**：真实硬件客户端只有一块，其余是 PC 上的 PyTorch 虚拟客户端；Algorithm 1 写的 Parallel 在实践中退化为 Sequential，串口的点对点拓扑也不支持真并行。

### 实验设计的不足

- **数据集单薄且自采**：CNdigits 仅 350 条、每类 50 条、作者自录（单一说话人偏置），ENdigits 7000 条取自 Speech Commands 的子集。均无说话人构成、信道条件说明。
- **关键对比存在混杂变量**：13.89% 的优势比较的是"大 CNN（SFL）"对"小 MLP（FL 上限）"，容量与训练方案绑死，无法分离"SFL 算法增益"与"模型容量增益"；缺集中式训练上界、缺多种子重复、缺统计显著性。
- **部署侧证据链断裂**：量化后精度、模型体积、板上延迟、能耗全部未报告，且作者承认最终板上部署与测试未完成——第三条贡献（推理闭环）停在"转换成功"而未到"实测跑通"。
- **文稿完成度低**：会议模板占位符未清除、硬件位数笔误（"2-bit"CPU）、参数算术与数值不自洽（650×25+25×7 写作 4725）、图表坐标轴信息在转档中受损，引用其具体数字时应回对原文。

### 未来可能的改进方向

论文自列四条（第 5.5 节），结合深读可扩展为：其一，**蓝牙通信**替代串口，摆脱有线连接、贴近真实部署形态；其二，**板上数据采集与标注支持**——让原始数据真正原生 于设备而非 PC 模拟，补齐 SFL 隐私故事的最后一环；其三，**多客户端真并行训练**，需要通信拓扑与聚合调度重设计；其四，**即时部署流水线**——全局模型一收敛，服务器自动产出压缩量化版本下发，把本文手工完成的转换链路自动化。笔者补充三个更有价值的方向：对切割点深度与通信量做系统消融，找到"板上内存-串口流量"的帕累托前沿；实测模型反演攻击下激活+标签泄露的风险并与防御方案（如[6]）叠箱验证；用差分隐私噪声或梯度压缩降低每步通信量，回应 SFL 的两大固有弱点。对 KWS 工程师而言，本文真正可带走的是那个非对称结构：**训练态内存四倍于参数量、推理态可压到参数量的四分之一，用 SFL 把训练搬到服务器、用量化把推理收回设备，两端各自越过了 256KB SRAM 的墙。**
