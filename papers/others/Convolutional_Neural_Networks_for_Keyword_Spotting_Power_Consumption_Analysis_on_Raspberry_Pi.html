别再只报参数量：外部功率计怼上树莓派——精度-功耗的帕累托前沿长这样

首个边缘硬件功耗实证树莓派 3 + 外部功率计架构维度系统扫描深度比宽度费电帕累托甜点 4-6 层
Convolutional Neural Networks for Keyword Spotting: Power Consumption Analysis on Raspberry Pi · Raphael Tang / Weijie Wang / Zhucheng Tu / Jimmy Lin（滑铁卢大学）· 2018 · arXiv 1712.01961
一句话：在树莓派 3 上用外部功率计实测多组 CNN 配置（深度/宽度/核大小/池化）的推理功耗——紧凑模型功耗降 50-60% 只掉 1-2 个点；同参数量下浅宽比深窄省电（访存次数决定），4-6 层 + 64-128 通道是甜点，「真机实测」从此进入 KWS 论文标配。

1问题：文献的集体盲区

TL;DR
  • 常开 KWS 的能效与精度同等重要——但文献几乎只报精度和参数量，不测真实硬件功耗。
  • 参数量 ≠ 功耗：内存访问模式 · 访存次数 · 算子实现都掺和——FLOPs/参数量只是粗代理。
  • 本文补空白：真机 + 外部功率计，扫深度/宽度/核大小/池化四个架构维度。
图 1 · 机制全景：三重盲区 → 实验设计（树莓派 3 + 功率计 + 四维度扫描）→ 三个核心发现 → 关键数字。

2机制：为什么深度比宽度费电

访存次数的账

深窄网络层数多——中间激活的读写次数多；浅宽同参数量访存少，功耗更低。

卷积层是功耗大头

大核（7×7）计算与访存双涨；通道数近似线性拉高功耗。

测量方法论

外部功率计记录推理期功耗曲线 → 平均功耗与能量/推理；batch=1 模拟常开单流。

可复现流程

GSC 35 词 GPU 训练 / Pi 上推理——一套后续研究可照抄的功耗测量协议。
图 2 · 左：同参数量的两种体型对比（深窄 10×32 vs 浅宽 4×128）——访存次数决定胜负；右：功耗的真实构成与「FLOPs 只是代理」的推论。
推理功耗 ≈ 计算能耗 + 内存访问能耗（权重读取 + 中间激活读写） 同参数量：层数 ↑ → 访存次数 ↑ → 功耗 ↑
人话：模型费不费电不只看算多少乘加，还要看「来回搬多少数据」。深而窄的网络像跑很多趟的小货车，浅而宽的像跑一趟的大卡车——货一样多，趟数少的省油。所以端侧模型别急着堆深度，先算算要搬运几次。

4边界：一块板子的结论

单平台结论

仅树莓派 3 的 ARM CPU——MCU/DSP/NPU 的功耗特性差异巨大，不能直接推广。

架构覆盖不全

只测了 CNN——RNN/Transformer/CRNN 在 CPU 上的功耗特性未比。

软件栈未控

TFLite vs ONNX vs 自研实现在同硬件上功耗可能差很多——论文未充分讨论。

任务口径差异

GSC 35 词分类 ≠ 真实唤醒词二分类（误唤醒率要求更严）。

无量化评估

INT8/INT4 量化对功耗的影响（内存带宽红利）未测。

5判断：能带走的三句话

JUDGEMENT

部署指标必须在部署硬件上量：FLOPs 和参数量是论文友好但工程失真的代理——功耗、延迟、内存峰值只有真机能给出真相；做边缘 AI 评估时「没上真机」本身就是结论的边界条件。

内存访问是被低估的功耗来源：同参数量下深度增加访存趟数——「浅而宽」常常比「深而窄」省电；这与 later depthwise/NAS 的结论互相印证：端侧架构的第一性原理是数据搬运最小化，不是表达力最大化。

帕累托前沿把「多省算力」变成可谈判的空间：甜点之后每瓦买到的精度骤减——产品定预算时对着前沿选点，比追逐榜单 SOTA 更接近工程最优。
